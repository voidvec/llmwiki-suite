# llmwiki-suite vs. local RAG — a fair comparison

## 1. One-liner

**Classic RAG slices & embeds your notes at query time; llmwiki compiles them once at import time — so your index is always fresh and never decays.**

## 2. Comparison table

| Dimension | Typical local RAG (Ollama + embedding, LocalGPT, LlamaIndex personal) | llmwiki (compile) |
|---|---|---|
| **When the work happens** | At query time — slice + embed every question, retrieve on the fly | At import time — frontmatter, links, BM25+wikilink index built once |
| **Index freshness** | Stale if you don't re-embed nightly; re-embedding is slow and expensive | Build once per change (`llmwiki ingest --apply`); index follows your notes |
| **Dependencies** | Embedded models (sentence-transformers / Ollama), vector DB, chunking knobs | **Zero** third-party Python deps; pure BM25 + wikilink graph |
| **Offline / privacy** | Often local; model size and memory heavy | Fully local, tiny footprint, plain files + JSON index |
| **Query latency** | Embed query + vector search per question | Keyword + graph retrieval — sub-second on a mid-sized vault |
| **Complexity** | Chunk size, overlap, embedding model choice, re-embedding pipeline | `init` → `ingest --apply` → `query`; three commands |
| **Transparency / audit** | Black-box vector similarity; hard to explain why | Every answer cites the actual notes it was compiled from; lint & eval are first-class |

## 3. Why "compile" fits personal notes (3 arguments)

1. **Personal vaults change in small, continuous increments.** A compile step amortizes the cost: you pay once per note, and every later query is cheap. RAG pays embedding + slicing cost on *every* query against a snapshot that may already be outdated.
2. **Index freshness is a feature, not a chore.** With RAG you either re-embed nightly (slow, batch) or answers silently drift from your latest notes. llmwiki runs the compile on every import, and its health score (D1) surfaces "this note is stale" instead of quietly degrading recall.
3. **Auditability wins trust.** Compiled links + lint-report make it explainable *why* a note was returned. For a personal knowledge base you can't typically defend a black-box retriever the same way.

## 4. When RAG is still better (honest caveats)

1. **Heterogeneous, dense corpora.** If your notes contain PDFs/Docs/tables needing semantic similarity across embeddings, a compiled keyword+link index can undercut semantic retrieval. Compile shines on Markdown-first workflows.
2. **Semantic queries keyword search can't parse.** "What did I think about X over time?" NN retrieval handles paraphrases better than pure BM25. Our wikilink graph helps some; it is not a universal semantic layer.
3. **Compile is a workflow choice, not a physical law.** Both are valid; compile trades per-import cost for per-query speed and freshness. Hybrids (BM25 + small embedding optional layer) are planned as L1/later — not a today feature.

## 4. Where the numbers stand (real, not synthetic)

On our `testkb` (8 eval queries over real notes), the current baseline (2026-08-31):

- **contextual recall@4 = 1.0** — all 8 queries hit the right note in the top-4
- **MRR@4 = 1.0** — top-1 hit on every query

Setup: BM25 + wikilink graph retrieval, zero embeddings, plain Markdown. The baseline is enforced by a CI gate (recall ≥ 0.95 / MRR ≥ 0.90) so it can't silently decay. Full eval report generated by `llmwiki eval` (JSON + SVG), reproducible in <1s on a kit.

## 5. Scope of comparison (consistency statement)

- "Local RAG" here means the typical **Ollama/embedding + keyword-chunking personal-brain** approach (nashsu-style free-ask / LocalGPT / naive LlamaIndex). We compared it on the **personal-notes server use-case**, not on enterprise PDF pipelines.
- Numbers in §4 are **ours** (a single-vault audit); we do not publish synthetic benchmarks for the RAG railing side — for a fair comparison, deploy and measure on your own vault (15-minute trial).

## 6. Bottom line

llmwiki is a **compile-first workflow tool**, not a drop-in RAG replacement. For developers who live in Markdown and want a searchable memory that *never decays* and *can be audited* — it's a better default than running a nightly re-embed job. For everything else, RAG still has its place — feed-back is welcome.
