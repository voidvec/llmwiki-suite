# LlmWiki 自进化路线图：从一问一答到主动思考与建议

> 面向：想让知识库**不只是回答器**，而是能自己沉淀经验、发现缺口、主动给建议的人。
> 本路线图把「知识库自进化」拆成可落地的四个阶段，每阶段都能独立验收、增量推进。

---

## 0. 现状：为什么「一问一答」低级

当前 `llmwiki` 是**纯被动的检索 + 生成**（`llmwiki query` / 微信通道 / serve）：

```
问题 ──► 调用方想起来才问 ──► 召回(BM25+link) ──► 生成 ──► 一次性答案（丢弃）
```

缺陷（图里那条浅色链路）：
- **无记忆**：每次回答是独立事件，不积累「知识库被问过什么、缺什么」。
- **无反馈闭环**：答完就完，不知道用户满不满意、哪些 query 经常查不到。
- **无主动动作**：知识库不会在没人问时自己整理、发现断链 / 过期 / 缺口。
- **无自我意识**：不知道「我知道什么、我不知道什么」，无法主动给出建议。

这条路线图的终局是：知识库**平时在学习、同时在待命**，主动发现问题、整理结构、
提示用户「最近别老查美食，你库里没有美食文档」——而不是只等被问。

---

## 1. 阶段 L0：固化「被动回答」的质量底座（已具备能力）

> 目标：让被动回答器本身**可衡量、可优化、可扩展**，这是后面一切的地基。

| 能力 | 现状 | 为什么是地基 |
|------|------|--------------|
| `llmwiki index` | ✔ BM25 + wikilink 图 | 召回基础 |
| `llmwiki eval` | ✔ recall@K / MRR + `--chart` | **给召回定标尺**，进化才有「是否变好」的判据 |
| pre-commit / CI | ✔ 质量门禁 | 每次改动不破基线 |
| `llmwiki serve` | ✔ 微信/企业微信/飞书/Telegram | 已有 4 个通道，进化后回写有渠道 |
| P3 索引新鲜度 | ✔ 指纹比对告警 | 已具备「感知内容变了」的最小能力 |

**验证**：`llmwiki eval --chart` 能画出 recall@K；`serve /healthz` 通道全部列出。

> 现状已经给了「自进化」的第一块砖：**索引新鲜度检测**——它已经是「知识库感知自身已过期」的雏形。

---

## 2. 阶段 L1：增量记忆与回放（从「无状态」到「有记忆」）

> 一句话：知识库开始**记住被问过什么、答得怎么样**，并在晚自习时重放、纠错、补课。
> 这是「自进化」的**最核心第一步**——没有记忆就没有进化。

### 2.1 三个新数据文件（零依赖，直接落地）

```
<库根>/
  kb-memory.json      # 「被问过什么 + 答得如何 + 缺口」的持久记忆
  kb-suggestions.md   # 主动给用户看的「建议清单」（人读、可 diff）
  kb-evolution-log.md # 自我修改的审计日志（改了什么、为什么、谁改的）
```

`kb-memory.json` 示例：

```json
{
  "queries": [
    {"query": "如何配置 lint 自动化", "asked_at": "2026-08-20T10:12",
     "top_hit": "docs/llmwiki-tutorial-01-system.md", "rank": 1,
     "answered_ok": true}
  ],
  "gaps": [
    {"topic": "美食菜谱", "times_missed": 3,
     "suggestion": "库内无美食类文档，考虑补充"}
  ]
}
```

### 2.2 四个新命令（加入 CLI）

```bash
llmwiki observe   # 每次回答后：记录 query + 命中/未命中 + 反馈 → 追加到 kb-memory.json
llmwiki nightly   # 「晚自习」：重放近期问题、对未命中 query 做召回诊断、找断链/过期/缺口
llmwiki suggest   # 基于 memory + nightly 产出 kb-suggestions.md 主动建议清单（gap 去重、按热度）
llmwiki evolve    # 机器学习级一步：integ = observe + nightly + suggest 的串联入口
```

### 2.3 让「自进化」发生的最小闭环

```
回答用户的过程中：
  observe 记录 query/rank/gap →（任意时刻/定时）nightly 重放未命中 + taste 缺口
  → 生成长线建议 kb-suggestions.md → 用户可以同意（人工把建议落成笔记）或忽略
```

**最轻的「自进化」动作**（不自动改用户笔记，只自动维护系统级文件）：

1. `observe` 在每次 `answer` 后记录「问过什么、是否命中、rank、缺什么」；
2. `nightly` 定时（可用系统 cron / CI 夜间 job）扫 memory，重放 miss 查询、跑 `lint`、
   找出**说过「未找到」的地方**；
3. `suggest` 生成「建议写什么」「建议补什么链接」「哪里可能过期」的清单；
4. **人工一键采纳**：用户把「建议笔记」变成真实笔记（或加进 eval_queries 补充评估）。

> 关键：**L1 不做「自动改写用户笔记」**，只生成容易采纳的建议。让用户始终掌控内容，
> 但所有「知识库自己发现的问题」都被完整记录下来——这是 L2/L3 的输入。

### 2.4 验收标准

- [ ] 回答过的问题可从 `kb-memory.json` 查回（query、rank、是否命中、时间）；
- [ ] `llmwiki nightly` 能把 3 条以上「未命中/缺口」变成建议;
- [ ] `kb-suggestions.md` 可被人工一键采纳并提升 `llmwiki eval` 的 recall。

---

## 3. 阶段 L2：主动学习与建议（从「记录」到「主动」）

> 目标：知识库**在无人询问时也工作**：定期重放历史、主动给用户推送「该补充什么」、
> 根据使用频率自动整理热门 / 冷门条目。

| 新能力 | 机制 | 价值 |
|--------|------|------|
| **主动重放** | 每晚 `nightly` 把近期未命中 query 重跑 recall，若更新了文档则自动提议 `ingest/index` | 补漏不靠用户想起来 |
| **主动建议** | 根据 `kb-memory.json` 热度生成「最近被问最多 / 最缺」清单 -> `kb-suggestions.md` | 用户打开就知道「该关注什么」 |
| **过期感知升级** | P3 已检测索引过期；L3 增加「内容半衰期」：超过 N 月未更新的高命中文档推「该 review 了」 | 知识库自己维活 |
| **引用回廊** | 从答案中被多次引用的章节，自动提升其「权威度」标注 | 自组织的知识网 |

### 主动建议示例

```
┌─────────────────────────────────────────────┐
│ 🧠 本周建议（llmwiki nightly 生成）            │
├─────────────────────────────────────────────┤
│ 1. 你最近 7 天问「Kubernetes 排障」3 次，但     │
│    库里 0 篇相关笔记 —— 是否补一篇？            │
│ 2. docs/llmwiki-architecture.md 已 180 天     │
│    未更新，而你在上面犯过错，要不要 review？     │
│ 3. lint 发现 2 条断链，建议 `llmwiki lint` 修复 │
└─────────────────────────────────────────────┘
```

### 验证

- [ ] 知识库 30 天不动，仍能自动发现 1 条「高价值但过期」条目；
- [ ] 连续 3 天问同样未命中问题，`kb-suggestions.md` 出现「建议补这一条」。

---

## 4. 阶段 L3：自主进化（从「建议」到「自动修复 + 自主延展」）

> ⚠️ 这一阶段是**可逆 / 可关**的：默认只对 `kb-evolution.md` 内的草稿级变化与用户 review 的变更自动落盘；**不直接用机器学习改写既有笔记**。

### 4.1 自主闭环（受限问）

```
observe（记忆）→ nightly（分析缺口）→ 自主生稿（补丁/新增草稿）→
eval 回归（必须不降低 recall/MRR 才生效）→ 形成 kb-evolution/章节 → 人审一眼 → 合入
```

关键设计：**「自动写 + 自动验证 + 人审」三段式**，任何一步不通过都不落地。

### 4.2 三个新的自主动作

1. **自动补缺**：gap 命中频数 ≥ 阈值 且现有文档无相关内容 → 自动生成一篇「占位笔记」
   （`eval` 中标记为 `placeholder`），进入 `kb-evolution/` 目录，等用户确认；
2. **自动修复**：`lint` 发现的断链 / EOF 规范性（如空行），机器直接改（低风险）；
3. **自动回应**：对社区高问（你在飞书/Telegram 被问了 3 次以上）→ 自动把答案总结成
   「FAQ 笔记」建议，可被一键转为正式笔记。

### 4.3 验证

- **不改人的笔记，机器只改自己生成的东西**（加进 `kb-evolution/`）；
- 每次数据检查都在干净的 git 工作区（机器只 `git add` 自己的目录）；
- 若 `eval` 指标回退，自动回滚该笔记变更。

## 5. 路线图总览（可打印）

| 阶段 | 价值 | 关键动作 | 复杂度 | 里程碑 |
|------|------|----------|--------|--------|
| **L0 固化**（已完成） | 可衡量、可部署 | eval + 多通道 + 新鲜度 | ==easy | `recall@100%` |
| **L1 记忆** | 有记忆、有建议 | observe / nightly / suggest | 中 | `kb-memory.json` 有数据 |
| **L2 主动** | 主动发现、主动建议 | 主动重放 + 建议 + 过期感知 | 中 | 连续 3 天未命中 → 建议出现 |
| **L3 自主** | 自主修复 + 验证回滚 | 自我补丁 + CI 回归 + 人审 | 高 | 机器能补 1 条可审的笔记 |

## 6. 实施顺序建议（roadmap 前 3 项 = 第 9+7 项 的增量）

9. **评估图表**（已完成本次合并本）→ 让一切进化可衡量；
7. **飞书 / Telegram 通道**（本次已加）→ 让知识库有了「被问 + 可回」的真实触点；
1. **observe + kb-memory**（L1 第一阶段）→ 补全「被问过什么、缺什么」的记忆；
2. nightly 重放 + suggest（L1 完成）→ 有主动建议输出；
3. 过期感知 + 主动 FAQ（L2）→ 知识库主动维活；
4. 自主修复 + 验证（L3）→ 少人力的知识库自治。

---

## 7. 技术风险与边界

| 风险 | 缓解 |
|------|------|
| 自动改笔记破坏用户内容 | L1-L2 只生成「建议文件」，不碰用户 .md；L3 只动 `kb-evolution/` 并强制人审 + 可回滚 |
| 无用记忆膨胀 | `kb-memory.json` 上限（只保留最近 N 天 + 去重），格式可配 |
| 主动网络请求（定期调用 LLM） | 默认不自动触发网络；建议都走「夜间 cron / CI job」，可难 disable |
| 机器建议误导人 | 所有建议标注「**由 llmwiki 自动生成，请人工核**」，明确建议 vs 事实之分 |
